학습 목표

"누가, 무엇을, 어디까지 할 수 있나"
  • 인증 vs 인가 — Authentication(누구인가)과 Authorization(무엇을 허용)의 차이를 안다
  • RBAC 4대 리소스 — Role / ClusterRole / RoleBinding / ClusterRoleBinding을 작성한다
  • ServiceAccount — Pod 워크로드의 권한을 분리한다
  • X.509 / OIDC — 사용자 인증 흐름을 이해하고 직접 사용자를 만든다
  • Pod Security Admission — 네임스페이스 단위 Pod 보안 정책을 적용한다

RBAC 4대 리소스 조합

권한(Role)과 부여(Binding)를 범위(네임스페이스/클러스터)로 조합
리소스범위역할
Role네임스페이스해당 NS 안의 권한 규칙 정의
ClusterRole클러스터 전체클러스터 범위 권한 or 여러 NS 재사용
RoleBinding네임스페이스주체(User/SA)에게 Role/ClusterRole을 NS에 부여
ClusterRoleBinding클러스터 전체주체에게 ClusterRole을 전 클러스터에 부여

ServiceAccount & Pod Security Admission

워크로드 권한 분리 + 네임스페이스 Pod 보안
ServiceAccount

워크로드의 신원

  • Pod에 SA 할당 → 해당 권한으로만 API 호출
  • Token(1.24+ 프로젝티드·단명) 자동 마운트
  • 예: Jenkins SA는 ci NS만, prod는 read-only
PSA

3 레벨 × 3 모드

  • 레벨: privileged / baseline / restricted
  • 모드: enforce(차단) / audit(기록) / warn(경고)
  • NS 라벨로 적용 · restricted = runAsNonRoot·drop ALL

라이브 실습 — RBAC & 권한 검증

사용자를 만들고 권한 범위를 확인
# 인터랙티브 RBAC 스크립트 (SA→Role/Binding→권한테스트→X.509 사용자) $ ./k8s-rbac.sh # alice 사용자 권한 영향 범위 검증 $ kubectl auth can-i --list -n dev --as=alice $ kubectl auth can-i create deployments -n prod --as=alice # no $ kubectl auth can-i create deployments -n dev --as=alice # yes
